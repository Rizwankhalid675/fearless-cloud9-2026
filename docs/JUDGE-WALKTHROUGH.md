# For judges

Everything here is checkable in about five minutes. Nothing below is an assertion
you have to take on trust; each claim says how to verify it.

## The three-minute path

1. Open the live board. It starts on game 1 with all 173 champions available.
2. Press **Load a demo series**. You are now at game 4 of a best-of-five with
   **30 champions burned** by the first three games. The counter reads
   *136 available, 37 gone*.
3. Scroll the pool. Burned champions have not disappeared — they are struck
   through, each carrying a coloured chip naming the game that took them.
4. Press **Ask the advisor**. The banner reads **4 of 5 blocked by the rules
   engine**. Each blocked suggestion is struck through with the engine's own
   reason: *"Aatrox is burned — blue picked it in game 1."*
5. Type `amb`, press Enter. Ambessa locks into red's pick; the clock starts.
6. Press **Export series**, reload the page, press **Import series** and choose
   the file. The whole draft comes back.

That is the product. The advisor proposed five champions; deterministic code
refused four of them and said why.

## The one architectural claim

**No suggestion reaches the screen without the rules engine's verdict attached.**

There is exactly one function that decides legality —
[`legalityOf()`](../src/engine/fearless.ts) — and exactly one path from an advisor
to the UI — [`gateSuggestions()`](../src/advisor/gate.ts), which is four lines. The
pool grid, the draft-order state machine and the suggestion list all call
`legalityOf`; none re-derives availability. That is why the board and the advisor
cannot disagree, and it is what makes the whole thing testable against arithmetic.

## How to verify the numbers

```bash
git clone https://github.com/Rizwankhalid675/fearless-cloud9-2026
cd fearless-cloud9-2026 && npm install
npm test        # 102 passing, 10 skipped, no network, no API key
npm run measure # regenerates docs/RESULTS.md from scratch
```

| Claim | Where it comes from | How to check it |
|---|---|---|
| Engine exact on 10/10 series states | `docs/RESULTS.md` §1 | Each fixture's expected pool size is **arithmetic written out beside it** in `tests/fixtures/series.ts` (e.g. "three games, 30 distinct picks: 173 − 30 − 0"). None came from `legalPool()`. |
| Gate refused 21 of 50 (42%) | `docs/RESULTS.md` §2 | `npm run measure` re-runs it. |
| 102 tests passing | `npm test` | You will also see **10 skipped**. Those are `tests/keyboard.test.tsx` — a specification for accessibility work that is not done yet, written as tests and deliberately left `describe.skip` rather than as a TODO comment. See the limits section below. |
| 173 champions, patch 16.23.1 | `src/data/champions.json` | Committed snapshot, not a live fetch. |

Why ground truth matters here: a fixture generated by the code it tests only
proves the code agrees with itself. These were worked out by hand so the engine is
scored against something independent.

## Questions you might reasonably ask

**"The 42% is a strawman — you built a deliberately bad advisor."**
It is deliberately *pool-blind*, which is not the same thing. It ranks champions by
a static tier list and by which roles a side still needs, which is precisely what a
coach's priority sheet contains — and the category brief names the spreadsheet as
the thing to replace. The number measures the status quo, not a fabricated
opponent. It is also labelled as such in `docs/RESULTS.md`, with a "knows the pool"
column that reads "no". Point the optional model advisor at the same fixtures and
the column fills in with a different number; I left those rows **absent rather than
estimated** because I had no API key on the run that produced the file.

**"Where is the AI? This looks like a filtered list."**
The AI is the half that proposes, and the interesting engineering is the half that
refuses it. `src/advisor/llm.ts` is deliberately unvalidated: it will happily return
a champion that is burned, or one that never existed. The gate catches both, and a
nonexistent champion gets its own distinct reason ("no such champion at patch
16.23.1"). That failure mode is tested, in `tests/gate.test.ts`.

**"What if the gate itself has a bug?"**
Then the product is wrong, and that is why the engine is the most heavily tested
thing in the repo: **39 tests** across `tests/fearless.test.ts` (14),
`tests/draftOrder.test.ts` (13) and `tests/series.test.ts` (12), plus the 10
ground-truth fixtures checked in `tests/measure.test.ts`. It is pure — no clock,
no network, no React, no storage — specifically so it can be tested exhaustively.

**"Is this novel? Draft tools exist."**
The draft board is not the novel part and I would not claim it is. The claim is
architectural: availability is owned by one pure function, the advisor is
structurally incapable of bypassing it, and an illegal suggestion is **shown**
rather than hidden, with the game that burned it. The last point is a deliberate
product decision — a coach learns why a champion is gone instead of watching
options silently vanish.

**"Why no GRID data?"**
GRID is optional for every category. The engine's correctness does not depend on
match history, and adding a data source I could not verify offline would have made
the demo fragile. `docs/LIMITS.md` says so plainly.

**"What happens on a new patch?"**
The catalogue is pinned and will age — `npm run champions` refreshes it from Data
Dragon. An exported series file records the patch it was written against, so a
mismatch is visible rather than silent, and importing a champion the current
snapshot does not know reports the problem by name instead of crashing
(`tests/series.test.ts`).

**"Riot compliance?"**
Champion names come from Riot's Data Dragon, the static data Riot publishes for
community tools. **No Riot artwork, icons or splash art is used anywhere** — the
board is names and roles only, which is also why it stays legible at a glance. The
footer and README carry the standard non-endorsement notice.

**"Did you really use JetBrains tools?"**
See `docs/JETBRAINS.md`. It states exactly what was and was not used, and it was
written to be a record rather than a claim.

## What this does not do

Full list in [`docs/LIMITS.md`](LIMITS.md). The four that would matter most to you:

1. **Champion roles are a convenience filter, not ground truth.** They are widened
   from Data Dragon `tags`, which classify a champion rather than place it — Data
   Dragon tags Teemo "Marksman, Assassin". The role filter narrows the grid; it is
   never allowed to hide a legal pick, and a champion whose tags map to nothing is
   given every role rather than none.
2. **The priority tiers are one person's opinion**, cover 50 champions, and reflect
   one view of patch 16.23. Everything unlisted is tier 4.
3. **Two Fearless variants are implemented, out of more that exist.** Leagues also
   burn bans, or burn only from games a team won. The ruleset is a property of the
   series rather than a constant in the engine, so a third is a change in one file —
   but today there are two.
4. **Single user, single browser.** No accounts, no sync. The series file is the
   hand-off.

Also worth knowing: the clock is advisory and never gates a pick; below 860px the
board stacks rather than pretending to be one screen; and the model advisor sends
its request straight from the browser with the coach's own key, which is fine for a
local tool and would want a proxy in a team deployment.
